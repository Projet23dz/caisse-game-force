# ملاحظات المالك على دفتر الشروط — Cashflow Manager
التاريخ: 2026-11-24 — الإصدار 1.4 — الحالة: مُعتمدة من المالك (ما عدا النقاط المعلّمة «للتأكيد»)

## 1. تصحيح الاسم
- النشاط الأول: **Game Force** (محل الألعاب والـ PlayStation).
- النشاط الثاني اسمه **ETP** وليس OTP (ألياف بصرية، كاميرات مراقبة، أنظمة أمن).

## 2. الحسابات المالية لكل نشاط
- **خزينة / صندوق** (نقدي)
- **حساب بنكي**
- **حساب بريدي (CCP)**
- إمكانية إضافة حسابات أخرى لاحقاً.

## 3. التحويل بين الحسابات
- تحويل من حساب إلى آخر داخل نفس النشاط (مثلاً: من الخزينة إلى البنك، أو من CCP إلى الخزينة).
- ينقص من المصدر ويزيد في الوجهة، ولا يُحسب إيراداً ولا مصروفاً.

## 4. الشيكات (Chèques)
- نفس منطق العمل المعتمد في مشروع **PALM TOURS** (palm app).
- ⚠️ **للتأكيد:** لم أتمكّن من الوصول إلى محادثات PALM TOURS من داخل هذا المشروع. المطلوب من المالك إرسال قواعد الشيكات المعتمدة هناك أو تأكيد المقترح أدناه.
- المقترح المؤقت:
  - **شيك مستلم** (من زبون): مسجَّل في الحافظة ← مُودَع في البنك للتحصيل ← **محصَّل** (يزيد رصيد البنك) أو **مرفوض** (لا يؤثّر في الرصيد).
  - **شيك صادر** (لمورّد): صادر ← **مصروف من البنك** (ينقص رصيد البنك عند الصرف) أو ملغى.
  - بيانات الشيك: الرقم، البنك، الساحب/المستفيد، المبلغ، تاريخ الاستحقاق، الحالة، العملية المرتبطة.
  - أي شيك لا يؤثر في الرصيد إلا عند التحصيل أو الصرف الفعلي.

## 5. الشراء
- **نوع الشراء** (فئة/نوعية: أجهزة، ألعاب، معدّات تقنية...).
- **اسم المورّد** (الجهة التي اشترينا منها)، مع إمكانية إضافة مورّد جديد مباشرة من نموذج الإدخال، وحفظه لإعادة استعماله.

## 6. سجل التعديلات
- **حفظ وإظهار كل عملية تعديل** لمتابعة كل شيء: من عدّل، متى، القيمة القديمة، القيمة الجديدة، السبب.
- السجل ظاهر في واجهة البرنامج (وليس مخفياً في قاعدة البيانات فقط)، ولا يمكن حذفه.

## 7. الأدوار
- **Admin** (المدير العام): كل الصلاحيات.
- **Utilisateur** (مستخدم)، وله صفتان: **موظف** أو **مسؤول**.
- **المسؤول يرى البرنامج كما هو موجود على السيرفر.**
  - ⚠️ **للتأكيد:** هل المقصود أن المسؤول يرى كل البيانات والشاشات مثل الـ Admin (قراءة كاملة) دون صلاحيات الإعدادات والمستخدمين؟

## 8. صلاحيات المستخدمين (موظف / مسؤول)
الـ Admin يحدّد الصلاحيات لكل مستخدم **ولكل نشاط على حدة**، بخانات اختيار (✓/✗):

| الصلاحية | موظف (افتراضي) | مسؤول (افتراضي) |
|---|---|---|
| الوصول إلى النشاط (Game Force / ETP / ...) | حسب التعيين | حسب التعيين |
| الحسابات المسموح بها (خزينة / بنك / CCP) | الخزينة فقط | الكل |
| إضافة إيراد | ✓ | ✓ |
| إضافة مصروف | ✓ | ✓ |
| إضافة شراء | ✗ | ✓ |
| إيداع / سحب | ✗ | ✓ |
| تحويل بين الحسابات | ✗ | ✓ |
| تسجيل شيك / تحصيله / إيداعه | ✗ | ✓ |
| تسبيق أجر / دفع أجر | ✗ | ✓ |
| تعديل عملياته (الوصف، الفئة، الملاحظات) | ✓ نفس اليوم فقط | ✓ |
| إلغاء عملية (مع ذكر السبب) | ✗ | ✓ |
| رؤية أرصدة الحسابات | ✗ | ✓ |
| رؤية عمليات المستخدمين الآخرين | ✗ | ✓ |
| فتح / إغلاق الصندوق اليومي | ✓ | ✓ |
| تسوية الصندوق | ✗ | ✓ |
| رؤية التقارير ولوحة التحكم | ✗ | ✓ |
| التصدير (Excel / PDF / CSV) | ✗ | ✓ |
| رؤية سجل التعديلات | ✗ | ✓ |
| إدارة الفئات والمورّدين | ✗ | ✗ (يفعّلها الـ Admin) |

- سقف مبلغ اختياري لكل مستخدم (مثلاً: الموظف لا يسجّل مصروفاً أكبر من X دج دون موافقة).
- الصلاحيات مطبّقة على السيرفر وقاعدة البيانات، وليس في الواجهة فقط.
- كل تغيير في الصلاحيات يُسجَّل في سجل التعديلات.

## 9. تسوية الصندوق
- نوع عملية جديد: **تسوية** (Ajustement).
- عند الإغلاق اليومي، إذا كان هناك فرق بين الرصيد النظري والرصيد الفعلي:
  - **عجز** ← تسوية سالبة تُنقص الرصيد.
  - **فائض** ← تسوية موجبة تزيد الرصيد.
- التسوية **إلزامية السبب**، ومرتبطة بالإغلاق الذي أنتجها.
- لا تُحسب إيراداً ولا مصروفاً تشغيلياً، وتظهر في سطر مستقل في التقارير («فروقات الصندوق»).
- بعد التسوية يبدأ اليوم التالي برصيد مطابق للواقع.

## 10. الأجور وتسبيقات الأجور
### قائمة العمّال
- لكل نشاط قائمة عمّاله: الاسم، الوظيفة (تقني، بائع...)، الهاتف، **الأجر الشهري**، تاريخ البداية، نشط/غير نشط.
- العامل ليس بالضرورة مستخدماً للبرنامج.

### التسبيق (Avance)
- تسجيل تسبيق لعامل: المبلغ، التاريخ، الحساب الذي خرج منه المال، الملاحظة.
- ينقص رصيد الحساب **فوراً**.
- يُسجَّل على **شهر الأجر** المعني.

### دفع الأجر
- عند نهاية الشهر يحسب البرنامج تلقائياً:
  **الأجر الشهري + المكافآت − الخصومات − مجموع التسبيقات = الصافي المتبقي للدفع**
- يُدفع الصافي فقط (لا عدّ مزدوج للتسبيقات).
- حالة الشهر لكل عامل: غير مدفوع / مدفوع جزئياً / مدفوع.

### المتابعة والتقارير
- كشف لكل عامل: الأجور، التسبيقات، المدفوع، الباقي، شهراً بشهر.
- إذا تجاوزت التسبيقات الأجر يظهر **دَين على العامل** يُخصم من الشهر التالي.
- الأجور والتسبيقات تظهر في التقارير تحت بند **«الأجور»**، منفصلة عن المصاريف التشغيلية الأخرى.

## 11. نوع التطبيق والاستضافة
- **تطبيق سطح مكتب Windows (.exe)** بدل تطبيق الويب السحابي.
- البنية المقترحة (نفس نهج palm app):
  - **Electron** للواجهة (React + TypeScript، نفس التصميم الفاخر واللغات الثلاث).
  - **API Node.js** يعمل على جهاز السيرفر، وهو الوحيد الذي يتصل بقاعدة البيانات.
  - **PostgreSQL محلي** على جهاز السيرفر (PC رئيسي).
- **الأجهزة الأخرى:** تثبيت ملف .exe يتصل بالسيرفر عبر الشبكة المحلية (LAN).
- **من خارج المحل:** عبر **Tailscale** (شبكة خاصة مشفّرة، دون فتح أي منفذ على الإنترنت).
- **التحديثات:** ملف تثبيت جديد، أو تحديث تلقائي من السيرفر.
- **المرفقات:** تُحفظ على قرص السيرفر.
- **النسخ الاحتياطي:** نسخة يومية تلقائية لقاعدة البيانات والمرفقات، مع نسخة إلى خارج الجهاز (قرص خارجي أو سحابة).
- ⚠️ **للتأكيد:** ملف .exe لا يعمل على الهاتف. هل المطلوب أيضاً الوصول من الهاتف؟ (حل ممكن: نفس الواجهة متاحة عبر المتصفح على الهاتف من خلال Tailscale.)

## 12. الواجهة (UI/UX)
### المرجع
- الصورة المرجعية للمالك (ملفات المشروع) — لوحة تحكم «CashPro» داكنة فاخرة.
- العناصر المطلوب أخذها منها:
  - **قائمة جانبية** مع الشعار: لوحة التحكم، المؤسسات، العمليات، الخزينة، التقارير، المستخدمين، الإعدادات + بطاقة المستخدم + زر الوضع الليلي/النهاري.
  - **شريط علوي**: بحث سريع (اختصار Ctrl+K)، الإشعارات، اختيار اللغة، التاريخ.
  - **4 بطاقات مؤشرات**: الرصيد العام، إيرادات اليوم، مصاريف اليوم، مشتريات اليوم — مع نسبة التغيّر ↗/↘ ولون مميّز لكل بطاقة.
  - **بطاقة لكل نشاط** بشعاره وصورة خاصة به (يد تحكم لـ Game Force، كاميرا/ألياف لـ ETP) + بطاقة «إضافة نشاط».
  - **رسوم بيانية**: تطوّر مالي (إيرادات/مصاريف)، توزيع المصاريف (دائري)، تطوّر الرصيد (أعمدة)، أداء شهري، حصيلة سنوية.
  - **صفحة نشاط** بتبويبات: نظرة عامة / العمليات / التقارير / الإعدادات، مع بطاقة كبيرة لرصيد الصندوق.
  - **جدول العمليات**: فلاتر (النشاط، النوع، الفترة)، ألوان حسب النوع (إيراد أخضر، مصروف أحمر، شراء أزرق، تحويل برتقالي)، أزرار عرض/تعديل، ترقيم صفحات.
  - **الخزينة**: رصيد حالي، ملخص اليوم، زر «إغلاق الصندوق»، مؤشر الفرق (0 دج = OK بالأخضر).
  - **التقارير**: فلاتر سريعة (7 أيام، 30 يوماً، هذا الشهر، سنة)، تبويبات عام / حسب النشاط / مقارنة، زر تصدير.

### الشعارات
- شعار المحل **Game Force** مُرسَل من المالك (حرفا GF داخل معيّن، نصف أحمر ونصف أزرق داكن، مع دوائر بيضاء في الوسط، والاسم GAME FORCE تحته).
- **إمكانية تغيير الشعار من داخل التطبيق:**
  - شعار **لكل نشاط** (Game Force، ETP، ...) من صفحة إعدادات النشاط.
  - شعار **البرنامج** نفسه (القائمة الجانبية، شاشة الدخول، التقارير المطبوعة) من الإعدادات العامة.
  - رفع صورة (PNG / JPG / SVG)، معاينة فورية، قصّ وتوسيط، وإمكانية الرجوع للشعار السابق.
  - الشعار يظهر أيضاً في رأس ملفات **PDF و Excel** المصدَّرة.
  - كل تغيير شعار يُسجَّل في سجل التعديلات.

### الأنماط (Themes)
- **عدّة أنماط** قابلة للتبديل من الإعدادات، لكل مستخدم.
- **النمط الافتراضي «Game Force»** — ألوان مستخرجة من الشعار:

| الدور | اللون | الاستعمال |

| أحمر Game Force | `#E30613` (يتراوح `#D9040A`–`#FD0819`) | الأزرار الرئيسية، العناصر النشطة، التنبيهات المهمة |
| أزرق داكن Game Force | `#1F2A7A` (يتراوح `#131E70`–`#2C3584`) | القائمة الجانبية، البطاقات، الرؤوس |

  - ألوان الحالات تبقى واضحة وثابتة: إيراد أخضر، مصروف أحمر، شراء أزرق، تحويل برتقالي — مع تمييز الأحمر «مصروف» عن أحمر الهوية.
- أنماط إضافية: Midnight Black & Gold (مثل الصورة المرجعية)، Deep Navy، Emerald Dark، Premium Light (فاتح).

### مستوى الجودة
- منهجية **UI UX Pro Max** وما يماثلها لنتيجة احترافية:
  - نظام تصميم موحّد (ألوان، خطوط، مسافات، ظلال، زوايا) قبل بناء الشاشات.
  - خط عربي احترافي + خط لاتيني متناسق، أرقام واضحة للمبالغ.
  - دعم كامل لـ RTL (العربية) وLTR (الفرنسية/الإنجليزية).
  - تباين ألوان مقروء (معايير الوصول)، حالات hover/focus/loading/empty/error لكل عنصر.
  - حركات سلسة ومحسوبة (Framer Motion)، دون إبطاء البرنامج.
  - أيقونات احترافية موحّدة، ورسوم بيانية تفاعلية.
  - شاشات متجاوبة: شاشة PC عادية، شاشة كبيرة، وتابلت/هاتف إن تقرّر الوصول عبر المتصفح.
- طريقة العمل: **تصميم نموذج أولي (Mockup) ← موافقة المالك ← تنفيذ**.

7. هل يلزم الوصول من **الهاتف** أيضاً (القسم 11)؟
